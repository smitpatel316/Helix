## Bugs

### Blocker

**QAB-1 — BLOCKER, confirmed ×2 (Mac): second click on a graph inspector's MATCH "Choose…" destroys all windows and silently loses unsaved work.**
Repro (minimal): fresh window → Column A=[1..5] → XY Table X=[−2,−1,0,1], Y1=[10,40,70,95] →
Dose-Response graph + Scatter graph → in a graph inspector's MATCH section, click "Choose…" once
(only focuses the button; no menu opens), press Space (no-op), click "Choose…" again →
driver reports "windows could not be read", all Helix windows vanish.
First occurrence: same sequence on the dose-response graph's MATCH picker in the full QA project
(PID 8602; windows 14191 column_sdn + 14298 Untitled lost).
State after: process alive, main thread idle in `NSApplication` run loop (`sample` shows
`_DPSNextEvent`, 0% CPU — **not** a deadlock), System Events window count 0, no menu bar
(AX error −1719), Cmd+N creates no window, no crash report in
`~/Library/Logs/DiagnosticReports`, no Helix error lines in the unified log, WebKit XPC services
still alive. **No save/discard prompt ever appears** — the entire unsaved project is lost.
Only a process kill + relaunch recovers the app. The pre-existing unsaved column_sdn window was
lost this way and could not be restored.
Evidence: `qa/QA-LOG.md` "INCIDENT" + "BUG-2" entries; screenshots 10 (before), 13 (after recovery).

### Major

**QAB-2 — MAJOR, confirmed ×3 (Mac): graph canvas clipped by the inspector.**
With the inspector open in the 1000×700 window, the fixed 640×460 canvas is occluded on the
right: mean/error graph hid the D bar; dose-response graph hid X=0.5/1/1.5 points. Seen in the
pre-existing column_sdn window, the QA mean/error graph (shots 06 vs 07), and the dose-response
graph (shot 10). Hiding the inspector reveals the full graph; exports are complete (not clipped).
Evidence: screenshots `06-mean-error-inspector-open.jpg` vs `07-mean-error-inspector-hidden.jpg`.

### Medium

**QAB-3 — MEDIUM, confirmed headless + parser (Mac + Linux): `.pzfx` date-X import drops the
dates while warning they were kept as row titles.**
`test-corpus/pypzfx-x_date.pzfx`: file has `XFormat="date"`, an `XAdvancedColumn` with 50 date
strings ("16-Jan-2004", "9-Apr-2009", …), and an empty `RowTitlesColumn`.
`src/lib/pzfx.ts:257` computes `hasRowTitles` **before** the date branch; lines 286–289 copy the
dates into `rowTitleValues`, but line 381 still uses the stale `hasRowTitles=false`, so every
row's Title is `null` and the dates are lost — while the emitted warning says "the X values are
dates; the dates were kept as row titles." The numeric X values (days 0, 5.229…, 8.123…) are
preserved, so analyses still run, but the human-readable dates are gone and the message is false.
Repro: run `parsePzfx` on that file; `rows[0]` is `[null, "0", "120"]` instead of
`["16-Jan-2004", "0", "120"]`. No test covers `x_date` (checks.ts only covers the 6 testdata fixtures).
GUI verification of this file was not completed (import lane stopped before it).

### Low

**QAB-4 — LOW, confirmed headless (Mac + Linux): 2×2 "Chi-square (for reference)" is
Yates-corrected; Prism reports uncorrected.**
`src/stats/contingency/chi-square.ts` calls R `chisq.test(m)` (default `correct=TRUE`):
Helix 6.4160401 vs Prism-style 8.12030075. Fisher's exact (the primary result for 2×2) is
correct. Fix would be `chisq.test(m, correct=FALSE)` for the 2×2 branch (non-2×2 path unaffected).

### Minor / limitations

- **Cosmetic (Mac, GUI):** linear-regression intercept rendered as `−1.589e-15` (float residue)
  in the equation and table instead of 0.
- **Limitation (Mac, GUI):** dose-response graph's fitted curve requires X>0 (it fits 4PL on
  concentration), so log-X dose data gets points but no curve in either Log X or Linear X mode —
  while the analysis offers a 4PL "X is log(concentration)" model the graph doesn't. Message is
  clear and honest; points are fine.
- **Negligible / open (headless):** Tukey p-values in the far tail differ from scipy's
  `studentized_range.sf` by up to 1.5e-4 relative (RM) / 3.3e-3 relative (two-way, p~1e-15).
  Helix == R `TukeyHSD` to 1e-9 where the repo cross-checks, using the identical code path for
  all pairs — almost certainly scipy's far-tail inaccuracy, not Helix. No action recommended.
